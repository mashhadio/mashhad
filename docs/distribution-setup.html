مشهد (Mashhad) — Auto-update & Distribution

How new versions reach users, the one-time setup, and the per-release runbook.

Model: the source repo is private at github.com/mashhadio/mashhad, while the compiled installers + update metadata live in a separate public repo — mashhadio/mashhad-releases — as GitHub release assets, so the app and Homebrew fetch updates with no credentials. The public download site is served from that same public repo's gh-pages branch. (An Electron installer's app.asar is extractable by any user regardless — a private repo hides the history and tooling, not the shipped JS.)

Account: the mashhadio owner appears in exactly four places — change all four together: build.publish[0] in package.json, OWNER in site/release.js, the url line in homebrew-mashhad/Casks/mashhad.rb, and the release repo referenced in .github/workflows/release.yml.

On Windows and AppImage the updater checks the feed on launch, downloads in the background, and shows an Arabic banner with an «أعد التشغيل للتحديث» (Restart to update) button. On macOS the same banner appears but offers «نسخ أمر التحديث» / «تنزيل النسخة الجديدة» instead. It is a no-op in development and on unsupported targets.

The update feed

The feed is the GitHub releases of mashhadio/mashhad-releases. The app is pointed at it via build.publish in package.json:

{ "provider": "github", "owner": "mashhadio", "repo": "mashhad-releases" }

electron-updater reads latest.yml (or latest-linux.yml) from the newest published release and pulls the installer listed beside it. The macOS check in src/main/updater.js reads releases/latest/download/latest-mac.yml — a plain redirecting URL, not the API, so there's no rate limit to trip on launch. The Homebrew cask points at the tag-pinned asset URL (releases/download/v<version>/…), which never moves under it.

One-time setup do these first — nothing updates until they're done

  1. Push the source to GitHub. mashhadio/mashhad, private. The workflows in .github/workflows/ only run once the code is there. Also close any older public mirror of this code — a private repo here achieves nothing while the same source is readable elsewhere.
  2. Create a release token. A fine-grained PAT with Contents: read and write on mashhadio/mashhad-releases. Add it to the source repo as the RELEASES_TOKEN secret (Settings → Secrets and variables → Actions). The automatic GITHUB_TOKEN can't be used: it only has access to the repo running the workflow, and the assets go to a different one.
  3. Push the Homebrew tap. Copy the contents of homebrew-mashhad/ into mashhadio/homebrew-mashhad (the homebrew- prefix is what lets brew tap resolve the shorthand).
  4. Turn on Pages — in the public releases repo. Push once to main so the Site workflow creates the gh-pages branch, then in mashhadio/mashhad-releases: Settings → Pages → Deploy from a branch → gh-pages / (root). DNS for an apex domain needs four A records — 185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153 — plus a CNAME for www → mashhadio.github.io. The domain itself lives in site/CNAME and ships with the pushed content. Pages can't run from the private source repo on a Free plan — it needs Pro or higher. On Pro you could deploy Pages from this repo directly instead and drop the extra hop.
  5. Publish a first release. Clients can only update from something already on the feed — see the runbook below.

Releasing a new version

Bump the version in three files first so the tag, latest.yml, the download page, and the Homebrew cask all match: package.json, site/release.js (VERSION), and homebrew-mashhad/Casks/mashhad.rb.

git commit -am "release 1.0.1"
git tag v1.0.1 && git push && git push --tags

That's the whole build step. The Release workflow fans out across four native runners — ubuntu-latest, windows-latest, macos-14 (Apple Silicon) and macos-13 (Intel) — and uploads every installer to a draft release in mashhad-releases.

  1. Review the draft release in mashhadio/mashhad-releases and confirm all five artifacts are attached (.exe, two .dmg, .AppImage, .deb) alongside the latest*.yml files.
  2. Publish it. Nothing updates for users until the draft is published — that is the switch that flips the feed.
  3. Update the cask. Download both .dmg files from the release, then: 
    shasum -a 256 Mashhad-<version>-arm64.dmg Mashhad-<version>-x64.dmg
    Set version and both sha256 arm: / intel: hashes in Casks/mashhad.rb, commit, and push the tap.

Building by hand instead (no CI): npm run release:win / release:mac / release:linux with GH_TOKEN set do exactly the same upload. The dist:* scripts build without uploading anything.

Verify an update end-to-end: install an older version than what's on the feed, launch it → the banner should appear, download, and the restart button installs the new build. A first release can't be tested this way — there's nothing to update from, so cut a throwaway patch version to prove the path works.

How users install & update

Windows

Download and run Mashhad-<version>-x64.exe. Updates apply automatically in-app (banner → Restart to update).

Linux

chmod +x Mashhad-<version>-x86_64.AppImage && ./Mashhad-<version>-x86_64.AppImage

AppImage updates in-app. For the .deb, reinstall the newer package.

macOS (Homebrew — recommended)

brew install --cask mashhadio/mashhad/mashhad   # install
brew upgrade --cask mashhad                     # update

No explicit brew tap needed — Homebrew resolves owner/tap/cask shorthand against GitHub.

macOS (manual .dmg)

Download the arm64 (Apple Silicon) or x64 (Intel) .dmg, drag the app to Applications, then clear the quarantine flag once — the build is unsigned, so without this macOS reports it as damaged:

xattr -dr com.apple.quarantine "/Applications/مشهد.app"

Notes & caveats

  • unsigned Windows shows a SmartScreen prompt; macOS is Gatekeeper-quarantined (the cask clears the quarantine flag automatically). Real signing/notarization is a separate, later step — and the thing that would let macOS self-update like the other platforms.
  • verify once Apple Silicon requires at least an ad-hoc code signature to launch at all. Confirm the first arm64 .dmg actually opens on an Apple Silicon Mac; if it's killed on launch, add an afterPack hook running codesign -s -.
  • Versions must stay in lock-step: package.json version = git tag = filename = Homebrew cask version = site/release.js VERSION.
  • Both macOS jobs write a latest-mac.yml and the second overwrites the first. Harmless today (the macOS check only reads the version out of it), but it would matter if macOS ever self-updates — the surviving file lists only one architecture's .zip.
  • cross-arch ffmpeg-static downloads a binary for the host arch at install time, and skips the download if one is already present. CI sidesteps this by building each arch on its own native runner; for local cross-builds, scripts/ffmpeg-arch.js deletes the binary and re-runs install.js with npm_config_arch set. Passing that var to npm rebuild does not work — npm ≥ 11 strips it — and the result is an installer that silently ships the wrong ffmpeg.
  • billing Actions minutes are only free-and-unlimited on public repos. On a private repo they come out of the monthly allowance (2,000 min on Free) with multipliers: Linux ×1, Windows ×2, macOS ×10. A full four-platform release is therefore on the order of ~150–200 billed minutes, most of it the two macOS jobs — roughly ten releases a month before the allowance runs out. If that gets tight, drop the Intel mac job and ship arm64 only, or build macOS locally with npm run release:mac.
  • The repo has been public in the past, so treat any previously committed secret as exposed and rotate it.
